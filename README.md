# DeepSeek 大模型原理笔记

> 两天里跟 DeepSeek 的一问一答，按主题重组成 11 个章节。
> 从「大模型算不算在找规律」一路问到「残差连接加完，原来的信息为什么还在」。

---

## 这是什么

2026-09-29 ~ 09-30 两天，我用 DeepSeek 从零开始补大模型的原理。原始对话 **214 条消息、44.4 万字符**，覆盖了从 Tokenization 到 RLHF 的整条链路。

这份仓库是那批对话的整理结果。**不是**把每个会话导出成一个 Markdown——那种整理法读起来是流水账。这里做的是按主题重组：同一个概念跨会话问了四次，就合并成一章；一章的素材来自多个会话，就如实标注来源。

整理前后的对照在第 **[00-索引](notes/00-索引.md)** 里，包括一张来源矩阵。

## 整理原则

| 内容 | 处理 |
|---|---|
| 我的提问 | **全部保留**，原文呈现（笔误用 `[ ]` 补正，不改原话） |
| 模型的正式回答 | 保留实质内容，去掉检索角标、寒暄与重复铺陈 |
| 模型的内部思考过程 | **全部丢弃**（占原始体积 54%，24 万字符） |
| 被中止的废弃分支 | 丢弃 |

最终保留率约 45%（20.2 万 / 44.4 万字符）。**信息内容一条没丢，删掉的是思考过程和检索噪音。**

## 学到哪一步了，还差什么

这部分是诚实的自评——**哪些是真读懂了，哪些只是知道名字**。

**已经吃透的**：Tokenizer → 词向量 → 位置编码 → 注意力 → 残差 → FFN → Logits 这条链，加上反向传播与后训练三阶段。这是整批对话最硬的部分，**而多数入门材料恰恰跳过它**：讲完「注意力就是加权求和」就停了，不会讲 4096 维到底怎么切成 8 个头、z₂ 是怎么从 `a₁v₁ + a₂v₂ + a₃v₃` 加出来的。

**只是知道名字的**（这些概念在正文里都出现过，但从没被展开解释过）：

| 缺口 | 为什么重要 |
|---|---|
| **采样与解码**：温度 / top-p / top-k / 重复惩罚 | 调 API 每天要碰；也是「同一个 prompt 为什么两次回答不一样」的答案 |
| **显存账本**：权重 + KV Cache + 激活值 | 唯一能自己动手算出来的量；直接决定能跑多大的模型、多长的上下文 |
| **批处理与吞吐**：continuous batching / PagedAttention / prefill·decode 分离 | 决定并发能力和单次调用成本 |
| **评测**：评测集、回归测试、LLM-as-judge | 没有评测，任何一次改动都无法判断是变好还是变坏 |
| **RAG 全链路**：切块、向量检索、rerank、引用溯源 | 把静态语料变成问答系统的最短路径 |
| **微调实操**：数据格式、LoRA 配置、何时该微调而非 RAG | 需要和 RAG 做取舍判断 |
| **MoE**：专家数、路由、负载均衡、激活参数计费 | 当前主流模型（含 DeepSeek 自己）都是这个架构 |
| **多模态**：图像/音频如何进 Transformer | 只提到过「统一表示空间」 |

## 后续计划

**方向已经定了：Agent 工程师。** 下面这条路线是按这个岗位的权重排的，不是按「理解模型」的通用顺序排——同样的知识清单，换个目标，优先级就完全不同。

**第一批：补齐缺口**（按对 Agent 工程师的权重排序）

| 顺序 | 缺口 | 为什么排这里 |
|---|---|---|
| 1 | **评测** | Agent 成败靠评估不靠感觉，也是整个清单里唯一需要「精通」的一项 |
| 2 | **RAG 与上下文工程** | Agent 的本质是上下文管理：切块、检索、压缩、记忆 |
| 3 | **采样与解码** | 工具调用的格式稳定性、temperature 怎么设，全依赖它 |
| 4 | **工具调用与 MCP** | 从「会写 prompt」到「能编排系统」的分界线 |
| 5 | **微调实操** | 判断什么时候该微调、什么时候该用 RAG |
| 6 | 显存账本、批处理吞吐 | 要自部署才需要，否则了解即可 |
| 7 | MoE、长上下文 | 跟上主流架构 |

> 更细的取舍标准见 [11.6](notes/11-学习路线与职业定位.md)——那里有一张逐项的「流程环节 × Agent 工程师需要程度」对照表。

**第二批：动手线**（顺序不能乱）

1. **手写一个 ReAct 循环** —— 不用框架。目的就是看清每一步到底在调什么。
2. **接上检索与记忆** —— 处理长对话压缩与长期记忆。
3. **建一套评测** —— 任务成功率、轨迹评估、回归集。这一项决定你和其他候选人拉开多少距离。
4. **加 tracing 与日志** —— 能定位失败发生在哪一步。
5. **这时候再上 LangGraph / MCP** —— 你会知道框架替你做了什么。反过来先上框架的人，常常卡在「Agent 老是失败，但我不知道为什么」这一步出不来。

**第三批：训练去魅（不是方向）**

nanoGPT，本地跑通训练与生成的完整循环。要看清楚的只有三件事：**loss 怎么降下来、过拟合长什么样、超参动了会怎样**。两三天，跑完就放下。

> 三条**不做**的：不从零训大模型（那套数据管线和并行策略对 Agent 岗完全用不上）；不追论文前沿；不为了「完整」去补显存账本和批处理（除非要自部署）。

## 已知的信息损失

1. **8 张截图无法恢复。** 原对话里贴了 8 张截图，但导出文件只保留了文件名，原图在服务端，不在导出范围内。受影响的追问（尤其是注意力全图、Q·Kᵀ 转置图、残差加法示例）在笔记里保留了**完整的文字推理**，但视觉部分需要对照原图才能复现。清单见索引第五节。
2. **模型的思考过程全部丢弃。** 这是刻意的——24 万字符里大部分是重复推演。
3. **一处中止的重复提问**只保留了完整的那一次。
4. **笔记里的原始提问保留了口误。** 明显笔误用 `[ ]` 补正，方便日后判断哪些是笔误、哪些是当时真实的认知状态。

## 整理方法

想拿同样的方法整理自己的对话，核心逻辑只有三步：

1. 从 `chat_session.current_message_id` 沿 `parent_id` 回溯出「活跃路径」，沿途丢掉被中止的废弃分支；
2. 只保留 `REQUEST` / `RESPONSE` 两类 fragment，丢掉 `THINK`（通常占一半以上体积）；
3. **按 `message_id`（整数）排序，不要用 `inserted_at` 时间戳**——后者不可靠，会把问答顺序打乱。
